Two additional reporting boundary defects were corrected during verification. Streak grouping now explicitly uses UTC instead of the PostgreSQL session timezone. Summary/top-music comparisons use the same equal-length, nonoverlapping previous period as the chart and leaderboard. Actual summary and overall/artist/track/album streak queries pass against fixtures whose database session uses `America/Los_Angeles`, including listens at midnight, duplicate UTC dates, sub-30-second plays and historical end dates.

The freshness policy is request based: navigating to or refreshing a dashboard reads current committed history. An already open dashboard does not poll for newly ingested listens. A history change during rendering becomes visible on the next request; the current report remains internally consistent. Using one transaction trades independent query connections and persistent report-cache hits for that consistency. No throughput/load-test claim is made.

## Automatic deployment migrations

Web and service `dev`/`start` scripts run `packages/database/runtime/start.mjs` before launching Next or scheduling worker jobs. Web `preview` also uses this path. Build commands do not access the migration runner. The wrapper loads the same environment files as the corresponding application, then uses production dependencies and SQL assets resolved relative to the runner.

Concurrent instances share a PostgreSQL transaction advisory lock. Pending migration statements and normal Drizzle journal entries commit together; migration failure rolls back and exits before the application process starts. Lock acquisition times out after 120 seconds. Termination cancels active migration work and releases its lock; after launch signals and arguments are forwarded to the child.

Deploy using the existing package scripts, for example:

```sh
pnpm --filter @soundstats/web start --port 3000
pnpm --filter @soundstats/service start
```

All instances must use the wrapper for its concurrency guarantee. Runtime deployment artifacts must retain `packages/database/runtime`, `packages/database/drizzle` and production dependencies; the database package includes those assets in its packaging manifest. An entirely new, empty database still requires explicit baseline initialization with `db:push`. Existing SoundStats databases automatically apply registered migrations during normal startup. See [the database instructions](../../packages/database/drizzle/README.md).

The normal web startup path was exercised against the configured development database, `spotify-thing-dev`. The first start applied the existing additive import migration; the next start applied zero. All three new nullable columns and one journal entry were verified, and the listening-history row count and aggregate fingerprints were unchanged. The actual import-history query now succeeds. No production database or real worker jobs were started. The local development preview is available at `http://localhost:3000`.
