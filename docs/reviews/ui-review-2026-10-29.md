# SoundStats redesign: UI and UX release review

Reviewed 29 October 2026 against commit `c5e7f75`. **Recommendation: hold deployment for the P1 findings and resolve the P2 items before calling this a polished release.** The typography, restrained surfaces, intact music artwork, and shared page widths form a coherent visual direction. The larger weaknesses are misleading context and incomplete interaction states, rather than a need for another visual redesign.

This is a review, not an implementation. Application source and account data were not changed. Evidence screenshots are in [the adjacent folder](ui-review-2026-10-29-assets/). Screenshots contain development overlays; those overlays are not treated as product defects.

## Findings requiring fixes

Priority: **P1** = misleading data/action outcome; **P2** = significant usability, accessibility, or state gap. “Browser” means observed in the running app. “Source” means the code path is confirmed but its failure/success condition was not forced against real account data.

### UI-01 · P1 · A friend's statistics can look like the current user's

**Evidence: Browser + source.** Open a friend dashboard for a profile without `firstName`, for example `/dashboard?user=user_2tmGkaq4BNqE2idJbQrekZTC4b9&from=2026-09-01&to=2026-10-17`. It displays **“Your listening” / “Your sound, in view.”** above the friend's numbers. Following music links preserves that friend's ID correctly, but artist/track/album detail pages contain no visible listener identity at all. This is a presentation error, not evidence of a permissions failure.

**Fix/acceptance:** Show a persistent listener name/avatar and a clear “Back to your listening” action when viewing someone else. Reserve “Your” for the viewer. Keep the same owner context on details and their return link. Test named, username-only, and unnamed friends. Use one public display-name policy across social pages: the same existing profile currently appears as an email in Friends, “Listener” on the leaderboard, and “Your listening” on its dashboard.

**Locations:** `apps/web/src/app/dashboard/page.tsx:199`; `apps/web/src/components/music-detail-page.tsx:117`; `apps/web/src/app/friends/actions.ts:80`; `apps/web/src/app/leaderboard/_components/leaderboard-list.tsx:41`.

### UI-02 · P1 · Friend actions can imply success after a returned error

**Evidence: Source; no mutation performed.** `sendFriendRequest` returns `{ error }` for authentication failures, existing requests, unavailable profiles, and database failures. `UserSearch` awaits it without checking the result, then removes the person from results. Accept/decline/remove/cancel handlers in the friend cards also ignore returned error objects. A failed search is converted to an empty array and rendered as “No users found.” A `catch` does not handle these resolved error results.

**Fix/acceptance:** Inspect each action result; change/remove rows only after confirmed success. Show an inline error or actionable toast, retain the person's row, restore the button, and support retry. Give successful sends an explicit “Request sent” state. Search failures must differ from no matches. Verify resolved errors as well as rejected promises, with no false success or stuck pending state.

**Locations:** `apps/web/src/app/friends/_components/user-search.tsx:35` and `:56`; `apps/web/src/app/friends/_components/friend-list.tsx:37`, `:130`, `:225`; corresponding result contracts in `apps/web/src/app/friends/actions.ts`.

### UI-03 · P2 · Dark-mode destructive messages are difficult to read

**Evidence: Browser + measured styles.** On `/import` in Default dark, the overwrite warning uses `rgb(127,29,29)` text on the `rgb(32,35,40)` card: approximately **1.57:1 contrast**. The warning is especially important because it explains replacement of existing history. Shared `text-destructive` error messages inherit the same weak token.

**Fix/acceptance:** Separate destructive foreground and fill colours, or choose a readable error foreground for dark surfaces. Verify warning text, icons, borders, inline invite errors, and destructive buttons in both modes; small warning/error text should reach at least 4.5:1. Preserve adequate contrast for text on filled destructive buttons when adjusting tokens.

**Locations:** `apps/web/src/styles/globals.css:51`; `apps/web/src/components/ui/alert.tsx:12`; `apps/web/src/app/import/page.tsx:88`.

[Dark import warning](ui-review-2026-10-29-assets/import-dark.png)

### UI-04 · P2 · The phone date picker hides essential calendar controls

**Evidence: Browser.** Open the dashboard date picker at 390px or 320px. It retains two horizontal months. Most of the second month and forward navigation are off-screen, with no explicit scrolling cue. Presets also run off-screen. At 320 × 780 the popup consumes almost the entire remaining height. Document overflow is contained, but the interaction still requires discovering multiple horizontal scroll areas.

**Fix/acceptance:** Use a single calendar month on phones with both navigation directions visible; provide a compact, clearly discoverable preset control. Keep selected range and Cancel/Apply reachable at narrow widths and with reduced viewport height. Verify touch, keyboard, and focus return after Apply/Cancel/Escape.

**Location:** `apps/web/src/components/DateRangePicker.tsx:945` through the fixed `numberOfMonths={2}` at `:970`.

[390px date picker](ui-review-2026-10-29-assets/mobile-calendar.png) · [320px picker](ui-review-2026-10-29-assets/last-seven-days.png)

### UI-05 · P2 · “Last 7 days” selects eight dates; period semantics differ across pages

**Evidence: Browser + source.** On 29 October, selecting Last 7 days and applying produces `from=2026-10-22&to=2026-10-29`, with both dates included in queries. Last 30 days similarly spans 31 calendar dates. The leaderboard uses the preceding 7 × 24 or 30 × 24 hours instead. Comparable-looking filters therefore describe different windows. UTC charts also use presets constructed from the browser's local date.

**Fix/acceptance:** Decide on calendar versus rolling windows, label them accurately, and share the definition where comparisons are intended. A seven-calendar-day preset including 29 October should begin 23 October. Make the “Today” basis explicit and consistent with UTC queries. Test near local/UTC midnight and month boundaries.

**Locations:** `apps/web/src/components/ui-parts/DateSelector.tsx:45`; `apps/web/src/app/leaderboard/_components/leaderboard-data-fetcher.tsx:68`.

[Selected seven-day preset](ui-review-2026-10-29-assets/last-seven-days.png)

### UI-06 · P2 · Historical streaks incorrectly say “Played today”

**Evidence: Browser + source.** View `/dashboard?from=2026-09-01&to=2026-10-17` on 29 October. The populated streak list says “Played today” and “Not played today,” although those flags are evaluated against 17 October. The small summary note about the end date does not make the row's literal wording accurate.

**Fix/acceptance:** Use “Played on 17 Oct” / “Not played on 17 Oct,” or “Played on the selected end date,” for historical ranges. Identify the streak's as-of date beside its heading. Use “today” only for the current reporting day. Apply this to all three streak categories and accessible labels.

**Locations:** `apps/web/src/components/music-collection.tsx:89`; `apps/web/src/app/dashboard/_components/listening-streaks.tsx:35`.

[Historical streak labels](ui-review-2026-10-29-assets/historical-streak.png)

### UI-07 · P2 · File selection presents a disabled primary action and no selected-file review

**Evidence: Browser + library source.** The prominent “Choose File(s)” button is disabled in the ready state. The surrounding dropzone/text is the working selection target. After selection, the button becomes “Upload 1 file,” but the interface still shows generic instructions: the selected filename and a remove/change list are absent. The picker accepts every file type. This is manual upload mode; selection alone does **not** upload.

**Fix/acceptance:** Provide an enabled, clearly named selection button, then a distinct upload action. Show selected filenames, sizes, per-file validation, and removal controls before submission. State the 20-file limit and validate expected JSON filenames locally. Keep the overwrite warning beside the actual submission action. Verify selection by keyboard as well as pointer.

**Locations:** `apps/web/src/app/import/page.tsx:98`; `apps/web/src/lib/uploadthing.ts`; `apps/web/src/app/api/uploadthing/core.ts:38`. The disabled chooser and selected-state content come from the current UploadThing dropzone defaults.

[Idle uploader](ui-review-2026-10-29-assets/import-dark.png)

### UI-08 · P2 · Import completion has no durable processing status or recovery path

**Evidence: Source + visible flow; successful upload not performed.** The UI explains that statistics may take hours to appear, but only stores upload status in component state. “Upload complete” means queued, not imported. Reloading loses that acknowledgement; there is no user-facing queued/processing/complete/failed history to return to, or retry path for processing failure. A user cannot distinguish a slow import from a lost job and may upload the same archive again.

**Fix/acceptance:** Add a persistent import-job list for the signed-in user, showing filenames, queue/processing/completion/failure status, useful timestamps, and a safe retry or help action. Use “Files uploaded — processing pending” until ingestion succeeds. Link completed jobs to the relevant date range. Verify refresh, partial batch failure, and a processing error after storage upload succeeds.

**Locations:** `apps/web/src/app/import/page.tsx:16`, `:106`; queue creation in `apps/web/src/app/api/uploadthing/core.ts`.

### UI-09 · P2 · A blank required-in-practice invite limit silently becomes unlimited

**Evidence: Browser + source; submission not performed.** On Create an invite, uncheck Unlimited uses and leave Maximum number of people blank. The native input reports valid and Create invite stays enabled. The submit handler passes `undefined`, the same representation used for unlimited invites, despite the UI promising that the invite will stop at the specified count.

**Fix/acceptance:** Require an integer from 1–1000 when Unlimited uses is unchecked, show a field-level message, and validate the same rule on the server. Empty, zero, fractional, out-of-range, and non-numeric values must not create an unlimited invite. Unlimited should be an explicit, deliberate choice.

**Locations:** `apps/web/src/app/invite/_components/create-invite-form.tsx:38` and `:139`; `apps/web/src/app/invite/actions.ts:48`.

### UI-10 · P2 · The feed's empty state hides its 24-hour window and gives the wrong explanation

**Evidence: Browser + source.** The account has substantial history and two friends, but `/feed` says “Your feed is waiting for its first track” and suggests selecting more people. In fact, the query only includes the last 24 hours, which the screen never states. The same first-track message appears when no people are selected.

**Fix/acceptance:** Label recent activity “Last 24 hours.” Distinguish no selections, no friends, no recent activity, and a fetch error. For no selections, provide a working “Show everyone” action; for inactive existing friends, explain that there have been no plays in the current window. Do not imply that existing listening history is missing.

**Locations:** `apps/web/src/app/feed/actions.tsx:54`; `apps/web/src/app/feed/recent-listens.tsx:136`; `apps/web/src/app/feed/page.tsx:61`.

[Empty feed](ui-review-2026-10-29-assets/feed-empty.png)

### UI-11 · P2 · Feed filtering lacks a consistent scope and loading/error states

**Evidence: Browser for filter/header updates; source for populated/racing cases.** The page-level filter changes Recently played, while `CurrentListeners` independently selects every friend and receives no filter. The heading can say “Showing activity from 0 people” while live activity still uses everyone. Recent-listen reloads and pagination have no visible pending/error/retry state, and requests are not guarded against outdated responses after rapid filter changes.

**Fix/acceptance:** Apply the people selection to both sections, or put a clearly scoped filter within Recently played. Announce pending updates, prevent stale responses from replacing newer selections, and distinguish load failure from an empty result. Provide visible pagination feedback and a retry control. Test rapid changes, select-none/select-all, slow loads, and a failed next page with existing rows retained.

**Locations:** `apps/web/src/app/feed/page.tsx:79`; `apps/web/src/app/feed/current-listening.tsx:25`; `apps/web/src/app/feed/recent-listens.tsx:71` and `:89`.

### UI-12 · P2 · Leaderboard drill-down discards the listening period

**Evidence: Browser destinations + source.** Set All time and open a listener's row. Its link contains only `user`, so the dashboard defaults to its recent calendar window. For the current sample account, the leaderboard shows roughly 1,633 hours all-time while the default dashboard shows 1,863 minutes. The destination provides no explanation for this change in scope.

**Fix/acceptance:** Preserve the selected period in the drill-down, or make the scope change explicit before navigation. Coordinate this with UI-05, since rolling periods cannot be represented exactly by the dashboard's current whole-date filters. Rename the user-facing “Count” option to “Plays,” matching the row label.

**Locations:** `apps/web/src/app/leaderboard/_components/leaderboard-list.tsx:49`; `apps/web/src/app/leaderboard/ClientDropdown.tsx`.

### UI-13 · P2 · Chart values are available by hover without an equivalent keyboard route

**Evidence: Browser DOM + source.** Music-detail charts render SVGs with empty title/description elements, no focusable data-point navigation, and no accessible table of bucket values. Their only descendant with a `tabindex` is the tooltip wrapper at `-1`. A generic “Daily listening time” label describes the chart but does not expose its data. Dashboard legend controls do not provide equivalent access to individual bucket values.

**Fix/acceptance:** Enable and verify keyboard data-point navigation with meaningful announcements, and/or add an accessible “View data” table covering date, current period, and comparison period. Verify keyboard-only access to the information exposed on hover, including hourly and aggregated ranges. Retain accessible labels and the solid/dashed series distinction.

**Locations:** `apps/web/src/components/LineChart.tsx:628`; `apps/web/src/components/ui-parts/PlaytimeChart.tsx:68`.

### UI-14 · P2 · Admin switches have no accessible names

**Evidence: Browser DOM + source.** All nine switches in the three-user table lack an accessible label or labelled-by association. A screen-reader user cannot reliably identify whose Enabled, Premium, or Admin state a switch changes. Mobile horizontally scrolls the controls away from the identity column, compounding the problem.

**Fix/acceptance:** Name each control using both the affected person and setting, such as “Premium polling for [name].” Associate table headers correctly and announce pending/result states. Give search fields explicit labels rather than relying only on placeholders. Add a visible mobile scrolling cue or a compact row layout that keeps identity and actions understandable.

**Locations:** `apps/web/src/app/admin/_components/user-toggle-switch.tsx:51`; `apps/web/src/app/admin/_components/table-search.tsx:20`; `apps/web/src/components/ui/table.tsx`.

[Phone admin table](ui-review-2026-10-29-assets/mobile-admin.png)

### UI-15 · P2 · Invite landing pages offer impossible or redundant relationship actions

**Evidence: Browser + source.** Opening the current account's own active invite still offers “Accept Invite & Become Friends.” The landing passes only authentication state to the button, with no owner/already-connected state. A friend-of-friend page also lists the viewer as “You” alongside “Already Friends,” making the relationship model harder to understand.

**Fix/acceptance:** Render “This is your invite” with a sharing/manage action for the owner. For an existing friend, offer their dashboard or feed; for a pending request, show that state. Exclude the viewer from suggested friends, or render a distinct non-actionable “You” state. Verify anonymous, self, existing friend, pending, expired, used-up, and new-friend variants without relying on a rejected action to explain the state.

**Locations:** `apps/web/src/app/invite/[code]/page.tsx`; `apps/web/src/app/invite/[code]/_components/accept-invite-button.tsx:92`; `apps/web/src/app/friends/[userId]/_components/user-friends-view.tsx:192`.

## Further polish before sign-off

- **Mobile navigation Escape:** Reproduced on signed-out `/privacy` at 320px: open the menu, leave focus on its toggle, press Escape. The menu stays expanded. Its Escape handler is on the child navigation, so it works only after focus moves into that navigation. Handle dismissal at the shared header/document level and restore focus consistently. Location: `apps/web/src/components/ui-parts/NavBar.tsx`.
- **Access-denied recovery:** The dashboard's centered “Access Denied” state has no recovery action and uses a different layout/tone from detail privacy, not-found, and global-error screens. Reuse the shared state pattern with “Your dashboard” and “Find friends.” [Evidence](ui-review-2026-10-29-assets/access-denied.png); `apps/web/src/app/dashboard/page.tsx:102`.
- **Loading shapes:** Route status roles and skeletons exist, which is good. However, the generic row skeleton is reused for forms and admin analytics; charts can initially show a large empty surface before client rendering. Keep the final page's approximate geometry, retain a chart skeleton until the chart mounts, and test transitions with actual network/CPU throttling. This is a follow-up verification requirement, not a measured production latency claim. Locations: `apps/web/src/components/page-layout.tsx:78`, `apps/web/src/components/LineChart.tsx:628`, route `loading.tsx` files.
- **Compact music typography:** Several secondary mobile list labels are 8–10px; track Average listen uses `00:03:53` while surrounding time displays use human-readable hours/minutes. Keep readable supporting text and use an unambiguous `3m 53s` for the average. Locations: `apps/web/src/components/music-collection.module.css`; `apps/web/src/components/music-detail-page.tsx`.
- **Contact and help:** Privacy and Terms tell users to contact the project or use contact information on the website, but their contact sections contain no actionable link. Link the intended support destination directly. This is a navigation/content usability observation, not a legal finding. [Evidence](ui-review-2026-10-29-assets/privacy-contact.png); `apps/web/src/app/privacy/page.tsx:257`, `apps/web/src/app/terms/page.tsx:166`.
- **Dialog consistency:** Friend removal uses native `window.confirm`, while invite deletion uses the styled alert dialog. Use the shared dialog with the affected person's/invite's name, clear consequence, and consistent cancel/focus behavior. Clipboard actions should expose a failure state when clipboard access is unavailable rather than relying only on a successful copy path.
- **Diagnostics:** `/debug` displays a bare `null` when nothing is playing. If this route is intended for users, replace that with “Nothing is playing” and a useful next step; keep raw response data in an optional diagnostics disclosure.

## What is working

- The Gosha/Geist typography, content widths, restrained spacing, and Default dark/light surfaces read as one product across the major routes.
- Main artwork and music-card destinations retain separate matching Spotify links, without nesting anchors or placing controls over artwork.
- Music-detail links preserve the listener and UTC date parameters through artist/track/album navigation and Back to dashboard.
- Cards/List choices are independent for rankings and streaks; category and layout controls are named. Phone list layouts are substantially easier to scan than the old tables.
- Sign-in is reachable through the narrow signed-out menu, and checked home/privacy layouts avoid document-level horizontal overflow at 320px.
- Empty detail periods and missing pages explain the state and provide useful navigation. Invite deletion has a cancel-focused confirmation dialog.

## Validation and remaining release checks

Existing automated suites passed: `test:ui-review` **5**, `test:listening-chart` **6**, `test:music-details` **3**. **Nine PostgreSQL integration cases were skipped** because `TEST_DATABASE_URL` was not configured. These tests do not establish visual quality or cover the newly identified interaction gaps. No new application code or tests were written for this review.

Before deployment, run a populated recent/live feed and restored now-playing-widget session; successful/failed import processing with a disposable account; social and invite success/error transitions; auth cancellation/return URLs; keyboard and screen-reader checks; and slow-network loading/retry checks. Recheck 320px and 390px in both modes, with zoom/text enlargement and an on-screen keyboard. Finish by restoring any temporary theme/layout preferences used during testing.

Recommended implementation order: listener context and action-result correctness first; date semantics and historical labels next; import selection/status and dark error contrast; then feed state handling, invite variants/validation, and keyboard/accessibility gaps. Preserve the accepted visual direction while fixing these behaviors.
